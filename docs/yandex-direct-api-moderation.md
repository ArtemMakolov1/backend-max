# MaxPosty: описание проекта для модерации API Яндекс Директа

Актуальность: 2 августа 2026 года.

## Назначение приложения

MaxPosty — веб-сервис для владельцев и команд каналов МАКС. Раздел «Реклама»
позволяет пользователю отдельно подключить принадлежащий ему кабинет Яндекс
Директа, подготовить кампанию для продвижения сайта в РСЯ, отправить её на
модерацию, явно запустить показы, ограничить максимальную цену
клика, подобрать ключевые фразы через Wordstat и посмотреть статистику.

Интерфейс функции: `https://maxposty.ru/app/#/advertising`.

Публичная инструкция: `https://maxposty.ru/docs/yandex-direct/`.

Приложение работает только с прямыми рекламодателями. Агентские аккаунты,
неизвестные типы аккаунтов и представители без права `EDIT_CAMPAIGNS=YES`
переводятся в режим только для чтения. MaxPosty не пополняет баланс, не меняет
платёжные данные и не управляет кампаниями без действия пользователя.

## Авторизация и данные

В приложении Яндекс OAuth запрашивается право «Использование API Яндекс
Директа» (`direct:api`). Пользователь самостоятельно подтверждает доступ на
странице Яндекс ID. В production настроен фиксированный Яндексом callback
`https://oauth.yandex.ru/verification_code`: MaxPosty открывает страницу
авторизации в новой вкладке, а пользователь переносит показанный Яндексом код
в приложение. Попытка защищена PKCE и одноразовым `state`, привязанным к
сессии, пользователю и workspace.

Backend также реализует браузерный callback
`https://maxposty.ru/api/v1/advertising/direct/oauth/callback`, но этот поток не
используется текущей production-конфигурацией. Он может быть включён только
после регистрации точного URL в настройках OAuth-приложения и синхронного
изменения production-переменной.

После обмена кода выполняется `Clients.get`: проверяются прямой тип кабинета,
RUB, отсутствие архива, доступность РСЯ и `UNIFIED_CAMPAIGN`; сохраняются ID,
логин и ФИО текущего представителя (`ClientInfo`), валюта и grants.
`Clients.get` не возвращает часовой пояс: для создаваемых кампаний MaxPosty
явно применяет фиксированную продуктовую политику `Europe/Moscow`.
Несовместимый кабинет отклоняется до сохранения подключения с безопасным
reason code. Access token,
refresh token и срок действия хранятся только на backend в зашифрованном
versioned bundle с AAD-привязкой к workspace, аккаунту и логину. Токены не
передаются браузеру и не пишутся в журналы. Nginx не журналирует callback с
`code` и `state`. Отключение интеграции отзывает локальный доступ; интерфейс
предупреждает, что уже работающую рекламу надо сначала остановить в Директе.

Локально хранятся параметры кампании, ID объектов, состояния модерации,
неизменяемые desired/observed snapshots, hash, revision ID, подтверждения
критичных операций и журнал команд. Ответы Reports и Wordstat отдельно не
сохраняются.

## Последовательность методов

Все Direct-запросы идут в JSON API v501
`https://api.direct.yandex.com/json/v501`. Sandbox используется только для
совместимых v5 read-only проверок: sandbox не заявляется как доказательство
работы полного UnifiedCampaign-графа v501.

| Сценарий | Методы Яндекс Директа | Когда вызываются |
| --- | --- | --- |
| Подключение | OAuth authorize/token, затем `Clients.get` | Один раз по нажатию «Подключить»; token refresh — не раньше чем за 5 минут до истечения либо при необходимости |
| Разрешение регионов | `Dictionaries.get` (`GeoRegions`, `GeoRegionNames`) | При создании/изменении кампании и подборе Wordstat; точный результат кэшируется в памяти на 6 часов |
| Создание кампании | `Campaigns.add`, `AdGroups.add`, `Ads.add`, `Keywords.add`, `Ads.moderate` | Один durable workflow после явной отправки пользователем на модерацию |
| Проверка после создания | `Campaigns.get`, `AdGroups.get`, `Ads.get`, `Keywords.get`, `BidModifiers.get`, `AudienceTargets.get` | После каждого этапа записи и перед фиксацией verified revision; дополнительное чтение выполняется только при неоднозначном результате для безопасной сверки |
| Изменение выключенной кампании | `Campaigns.update`, `AdGroups.update`, `Ads.update`, `Keywords.update/add/delete`, затем те же `get` и `Ads.moderate` | Только после проверки свежих graph hash/revision/version и команды пользователя |
| Ручной/разрешённый автозапуск | `Campaigns.get` и полный graph read, затем `Campaigns.resume`, затем повторный `Campaigns.get`/graph read | Ручной запуск — после отдельного подтверждения; автозапуск — только после отдельного согласия на точный кабинет, кампанию, бюджет, период, graph hash и revision |
| Изменение предела CPC | `Campaigns.get`, `Dictionaries.get` (`Currencies`), затем provider-edit через `Campaigns.update` и полный verify | По открытию вкладки читаются стратегия и актуальные `MinimumBid`/`MaximumBid`; запись — только после фразы «ИЗМЕНИТЬ СТАВКУ» |
| Проверка изменений | `Changes.check`; при изменении — полный graph read | Только для локальных кампаний, наступивших в очереди lifecycle |
| Статистика | Reports API, `CAMPAIGN_PERFORMANCE_REPORT` | Только по запросу пользователя, диапазон 1–366 дней; поля Date, CampaignId, Impressions, Clicks, Cost, Conversions |

Wordstat не использует OAuth-токен Директа. По отдельной пользовательской
команде backend вызывает Yandex Cloud Search API v2
`POST /v2/wordstat/topRequests` сервисным API key с правом
`yc.search-api.execute`. Передаются введённая фраза, до 50 результатов и ID
регионов текущей кампании. Нормализованный точный запрос кэшируется в памяти на
10 минут; одновременные повторы одного пользователя в том же workspace
объединяются в один логический запрос. Ограничение 400 символов применяется к
входной фразе; ответные ассоциации до 1024 Unicode-символов сохраняются для
copy-only сценария, пустые и более длинные provider-значения отбрасываются.

## Частота фоновых чтений

Worker просыпается раз в 15 секунд, но запрос получает только кампания, для
которой наступил `provider_next_check_at`. За один цикл берётся не более четырёх
кандидатов. Фактический минимальный интервал одной кампании зависит от её
состояния:

- модерация — 5 минут;
- provider draft / accepted — 15 минут;
- active — 30 минут;
- suspended — 1 час;
- rejected — 6 часов;
- неизвестное безопасно выключенное состояние — 15 минут.

Сначала вызывается `Changes.check` с курсором времени Яндекса и минутным
перекрытием. Если состав не менялся, полный graph read не выполняется. Курсор
продвигается только после успешного чтения и проверки указанного изменения.
Статистические отчёты, Wordstat и чтение ставок фоновыми задачами не вызываются.

## Лимиты, Units и повторы

- На одного рекламодателя в процессе разрешено не более четырёх одновременных
  запросов при документированном лимите Яндекса в пять.
- Из каждого ответа разбираются `Units` (`spent/remaining/daily`),
  `Units-Used-Login` и `RequestId`; snapshot используется для операционной
  диагностики и не считается биллинговыми данными.
- Повторяется только безопасное чтение (`get`, `check`, `checkCampaigns`,
  `checkDictionaries`) — максимум два повтора с bounded backoff. Методы
  `add`, `update`, `delete`, `moderate`, `resume` автоматически не повторяются.
- HTTP 429/503 и `Retry-After` создают cooldown рекламодателя. Ошибка нехватки
  Units (152) блокирует новые запросы на 60 секунд, превышение одновременных
  подключений (506) — на 2 секунды. Длинный `Retry-After` возвращается вызывающей
  стороне вместо удержания HTTP worker.
- Reports обрабатывает 200/201/202. Для 201/202 тот же byte-equivalent запрос
  повторяется через `retryIn`; общий backend timeout пользовательского отчёта —
  2 минуты.
- Wordstat-квота общей API key сериализуется в PostgreSQL между всеми репликами.
  Один логический запрос резервирует до трёх HTTP attempts, поэтому разрешено
  не более 3 логических запросов в секунду и 33 в скользящий час (максимум 9 и
  99 фактических HTTP-запросов при лимитах провайдера 10/с и 100/ч).
  Дополнительно действуют fair-use лимиты: workspace — 2/с и 20/ч,
  пользователь внутри workspace — 1/с и 10/ч. Локальная квота и ответ
  провайдера HTTP 429 возвращаются клиенту как HTTP 429 с `Retry-After`.
- Ответы ограничены по размеру; JSON/TSV, ID, даты, денежные значения и состав
  объектов валидируются fail-closed. Денежные параметры отправляются как целые
  значения в валюте × 1 000 000; UI использует minor units без float для записей.
- Справочник `Dictionaries.Currencies` кэшируется в процессе на 12 часов и
  объединяет параллельные загрузки; ключ разделён по live/sandbox client и
  рекламодателю, bearer token в открытом виде в ключе не хранится.
- HTTP 429 и ошибка Units 152 возвращаются как контролируемый HTTP 429,
  ошибка одновременных подключений 506 — как HTTP 503. `Retry-After` округляется
  вверх и ограничивается диапазоном 1–300 секунд; upstream details не выдаются.

## Защита от нежелательного расхода

- Глобальные server flags отдельно включают provider writes и auto-launch;
  одних OAuth credentials недостаточно.
- Создаваемая стратегия: Search `SERVING_OFF`, Network
  `WB_MAXIMUM_CLICKS`, Maps off, точный `WeeklySpendLimit` и необязательный
  provider-enforced `BidCeiling`.
- Лимит одной кампании MaxPosty — 10 000 RUB в неделю; суммарный атомарный
  лимит spend-capable кампаний workspace — 30 000 RUB в неделю.
- Любое критичное действие проверяет роль пользователя, connection ID,
  provider IDs, локальную version, graph hash и immutable revision ID.
- Внешнее изменение кампании или неоднозначный ответ API блокирует запись и
  запуск до повторного authoritative read и reconciliation.
- Автозапуск по умолчанию выключен. Согласие становится недействительным при
  изменении кабинета, кампании, бюджета, периода, версии или provider graph.

## Обработка ошибок

Ошибки валидации возвращаются пользователю без Direct-запроса. Ошибка прав или
истёкший OAuth-токен переводит подключение в `authorization_required`, отменяет
актуальность согласия на автозапуск и требует нового OAuth. Rate-limit и
временные provider errors не превращаются в повтор критической записи.
Неоднозначная запись остаётся в durable journal со стадией reconciliation:
backend читает фактический граф и продолжает только если однозначно доказано,
что предыдущий шаг применился или не применился.

# Бесплатный полный доступ для подтверждённого аккаунта

Ручной workflow `Manage approved account complimentary access` выдаёт или отзывает полный доступ к функциям без тарифных квот у одного заранее утверждённого аккаунта. Доступ распространяется только на пространства, которыми этот аккаунт владеет; участие в чужом пространстве не переносит туда привилегию. Роли, пароли, подписки, платежи и права в MAX/Яндекс Direct не меняются. Учёт использования и технические ограничения безопасности сохраняются.

Перед запуском установите адрес утверждённого аккаунта в secret `COMPLIMENTARY_ACCESS_ACCOUNT_EMAIL` защищённого environment `production`. Используется именно secret: обычная Actions variable не маскируется в заголовках шагов, где runner печатает environment. Сам workflow не принимает адрес аккаунта через input и не выводит адрес или ID пользователя в журнал. Аккаунт должен уже существовать и однозначно соответствовать нормализованному email и подтверждённой Yandex OAuth identity; неоднозначное или отсутствующее соответствие прекращает операцию.

Workflow запускается только вручную из `main` в исходном репозитории с protected environment `production`. Сначала требуется успешный CI и Security для точного commit, затем проверяются закреплённый SSH host, принятый исходный commit, работающий immutable image/revision, health и точная миграция039 с её SHA256. Операция разделяет production concurrency group и серверный deployment lock с обычным деплоем. На более новой миграции требуется пересмотреть operational-контракт прежде, чем расширять эту проверку.

После успешного деплоя миграции039 выполните `operation=inspect`. Это транзакция `READ ONLY`; она выводит лишь активность grant, число собственных пространств, факт изменения (`false`) и `owned_entitlements_unlimited`. Последнее поле проверяет в той же транзакции, что все активные собственные пространства имеют grant и неограниченные каналы, места и хранилище; при неактивном grant оно равно `false`. Затем при подтверждённом объёме задачи выполните `operation=grant`. Выдача проходит одной сериализуемой транзакцией через owner-only функцию `manage_account_complimentary_access`; immutable audit event записывается атомарно при изменении grant. Скрипт подтверждает неограниченные entitlement перед выдачей успешного результата. Повторная выдача уже активного grant не создаёт платёж и не меняет существующую подписку. `operation=revoke` отзывает именно эту привилегию и возвращает обычные тарифные ограничения; существующие данные не удаляются.

Функция выдачи и запись в таблицы grant/audit недоступны runtime-роли приложения. Скрипт соединяется напрямую из существующего PostgreSQL-контейнера как database owner; пароль не передаётся через host argv. Параметры email и оператора привязываются через literal-параметры `psql`, ошибки базы и промежуточные результаты остаются в приватном временном каталоге и удаляются после выполнения. В открытый журнал допускаются только проверенные числовые счётчики и boolean-поля. После операции проверяется публичный health.

Если CI, release/schema fence, lock, identity lookup или транзакция не прошли, workflow не должен обходить проверку. После неоднозначного клиентского результата сначала повторите `inspect`; grant/revoke идемпотентны по текущему состоянию и сохраняют аудит изменений. При отзыве аккаунт остаётся владельцем своих пространств, а доступ продолжает определяться обычными ролями и действительной подпиской.

Существующие подписки сохраняют возможность отмены и удаления платёжного метода. Выдача grant останавливает новые списания, но уже начатая попытка создания платежа без известного provider ID остаётся в счётчике ручной проверки вместе с обычными `manual_review` попытками: поздний ответ провайдера или проверенный webhook должен быть сопоставлен с исходной записью, а не потерян или повторно отправлен.

Проверка operational-политики в Linux: `bash deploy/tests/complimentary-access-policy.sh`. Она использует изолированный fake Docker, проверяет отказ до обращения к БД при дрейфе image/revision/health/lock, безопасную обработку private errors, scope параметров и read-only режим. CI запускает эту проверку вместе с остальными release/deploy policy tests.

Проверка реального `psql`-пути: `bash deploy/tests/complimentary-access-postgres-policy.sh <имя-тестового-контейнера>`. Допускается только явно указанный локальный контейнер вида `maxposty-…-pg-YYYYMMDD` с закреплённым PostgreSQL18.4 image и тестовыми `POSTGRES_USER=postgres`, `POSTGRES_DB=maxposty_test`; production-контейнер не подходит. В CI тот же тест получает точный `${{ job.services.postgres.id }}` и проверяет synthetic `TEST_DATABASE_URL`, режим GitHub Actions и отдельные тестовые `maxstudio_test` user/database. Тест создаёт отдельную БД и runtime-роль, применяет миграции с исходными default DML privileges, выполняет реальный операционный скрипт и проверяет grant→inspect→повторный grant→revoke, отказ самовыдачи через DML/EXECUTE, сохранение SELECT, checksum/identity fence и неизменность владения, ролей, подписок и платежей. Свои БД, роль и временные файлы тест удаляет; исходный тестовый контейнер остаётся доступен другим проверкам. Store-тесты отдельно проверяют функции, все возможности и расход квот.
